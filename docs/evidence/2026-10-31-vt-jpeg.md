## Result: STOP — hardware use remains unverified

Step 1 produced a compatible JPEG, but the hardware-attestation gate did **not** pass. With `kVTVideoEncoderSpecification_RequireHardwareAcceleratedVideoEncoder = true`, JPEG session creation, quality configuration and frame preparation all returned success. Querying `kVTCompressionPropertyKey_UsingHardwareAcceleratedVideoEncoder` returned **-12900 (`kVTPropertyNotSupportedErr`)**, so its value is **unavailable**, not confirmed true and not an observed false value.

The unchanged required-hardware session was allowed to encode the requested synthetic workload to gather format and performance evidence. No relaxed encoder specification, software-fallback setting, alternate pixel format, or repeated VT tuning was used. The probe exits **2** after the benchmarks because hardware use remains unverified. Successful required-hardware session creation is recorded separately from the unsupported attestation property; these results do not establish that hardware JPEG is absent on this Mac.

**No Step 2 bridge integration or Step 3 desktop measurement was performed.** `macos/DesktopBridge.m`, `src/desktop_frame.rs`, and all HID/bulk transport code are unchanged. The existing raw/software encoder remains the default. Under the task's stop rule, the next fallback implementation to evaluate is Rust libjpeg-turbo; it was not added in this spike.

## Reproduce

```sh
bash macos/build-vt-probe.sh
# Exit 2 means a failed or unverified hardware gate, even if format evidence exists.
MSI_VT_QUALITY=0.75 target/VTJpegProbe
cargo run --release --features hardware -- jpeg-profile /tmp/vt-probe.jpg
```

`build-vt-probe.sh` uses the bridge's ARC, blocks and optimization flags and framework list, adding VideoToolbox. It only builds `target/VTJpegProbe`, not the installed desktop app. No app code signing or screen-recording permission is involved.

The probe creates a 1920×720 `kCVPixelFormatType_32BGRA` CVPixelBuffer containing a colour gradient and text. It defaults `MSI_VT_QUALITY` to 0.75, validates the setting, and measures 100 frames at the selected quality plus 0.6 / 0.75 / 0.9 (without duplicate qualities). Frame timing is wall time from submission to the compression callback, excluding setup and file writing. Submitted frames are completed sequentially rather than measuring a pipelined throughput ceiling. The emitted content is synthetic and constant, so the byte counts are not estimates for a changing desktop.

On this synthetic scene, default quality 0.75 yields approximately 73 KB, below the 150–250 KB target. Quality 0.9 yields approximately 152 KB. The identical byte counts at 0.6 and 0.75 are observed results; the spike does not explain the encoder's quality mapping. No real-desktop quality, banding, cursor smoothness or end-to-end latency result is claimed.

This format check covers the saved quality 0.75 sample. The other 299 encoded frames were measured but not individually persisted or checked by the Rust CLI; no claim is made that all frames or all qualities passed the panel's format gate.
